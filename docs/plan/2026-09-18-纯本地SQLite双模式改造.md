# 计划：为 UGS Metadata Server 增加纯本地 SQLite 模式

日期：2026-09-18
状态：已完成
分支：`sqlite`

## 背景

原项目是一个 serverless 重写版本：Supabase Edge Functions（Deno + Hono）+ Supabase Postgres。
问题是使用门槛偏「云」：

- 想本地联调必须先装 Docker、起本地 Supabase（或直接连云端）；
- 想在内网单机自建，得额外维护一个 PostgreSQL 实例；
- 演示 / 试用场景下，配置成本远大于项目本身的价值。

目标：**让这个服务可以在完全没有外部依赖的情况下纯本地跑起来**，同时不能丢掉原有的
Supabase 部署能力，也不能改动 API（UGS 客户端必须零改动）。

## 需求确认（与使用方对齐的结论）

| 决策点 | 结论 |
|---|---|
| 改造范围 | **双模式**：保留 Supabase，新增 SQLite 后端，靠 `DB_DRIVER` 切换 |
| 运行环境 | **保持 Deno**，复用现有 Hono 路由代码 |
| 附加交付 | **Docker Compose 一键部署 + GitHub Actions 自动发布镜像** |

## 技术选型

| 方案 | 结论 | 理由 |
|---|---|---|
| SQLite 驱动 | `node:sqlite`（Deno 内置 Node 兼容层） | 零第三方依赖、零原生模块编译；内置 SQLite 3.53，已支持 `ON CONFLICT ... RETURNING` |
| 运行环境 | 继续用 Deno | `routes/` 几乎零改动；`Deno.serve` 直接可用 |
| `.env` 解析 | 自研 ~60 行解析器 | `Deno.loadEnvFile` 在当前版本不可用；`--env-file` 需要写进每条命令且不可控 |
| 自定义域名 | 不动 Cloudflare Worker | 只需把 `SUPABASE_FUNCTION_URL` 改成本地地址即可复用 |

## 核心设计

### 1. 驱动抽象层

新增 `drivers/`：

- `types.ts` —— 定义统一接口 `SqlTag`（可调用 + `begin` + `end`）与 `SqlDriver`。
- `postgres.ts` —— 把 postgres.js 收窄成 `SqlTag`，保持原有行为。
- `sqlite.ts` —— 用 `node:sqlite` 实现，内部做三件事：
  1. **方言翻译**：`${值}` → `?`；`NOW() AT TIME ZONE 'utc'` → `strftime(...)`；`::jsonb` → 去掉。
  2. **参数归一化**：`undefined` → `NULL`、`true/false` → `1/0`、`Date` → UTC 字符串、对象 → JSON 文本。
  3. **事务**：`BEGIN/COMMIT/ROLLBACK`，嵌套用 `SAVEPOINT`。

`db.ts` 变成门面：按 `DB_DRIVER` 选驱动并**懒加载**（第一次执行 SQL 时才连接），
对外仍导出 `sql`、`getOrCreateProjectId`、`findOrAddUserId`，因此 `routes/` 一行不用改。

驱动选择优先级：`DB_DRIVER` > 存在 `SUPABASE_DB_URL`/`DATABASE_URL` > 默认 `sqlite`。

### 2. 入口拆分

- `app.ts`：`createApp({ basePath })`，两种入口共用。
- `index.ts`：Supabase Edge Function 入口，`basePath = "/ugs-metadata"`。
- `serve.ts`：本地 / 自建入口，无前缀，读 `.env`，监听 `PORT`/`HOST`，支持优雅退出。

### 3. SQLite Schema

新增 `schema.sqlite.sql`，与 Postgres 迁移结构等价，差异仅在语法
（`INTEGER PRIMARY KEY AUTOINCREMENT`、`strftime` 默认时间、JSON 存 TEXT）。
打开数据库时幂等执行，首次运行自动建表，无需迁移工具。

### 4. 交付形态

- `Dockerfile`：两阶段（依赖预热层 + 运行层），非 root 用户，`/data` 数据卷，内置 healthcheck。
- `docker-compose.yml`：默认 SQLite，一键起。
- `docker-compose.postgres.yml`：可选的自建 Postgres 方案。
- `.github/workflows/docker-publish.yml`：先跑 lint / check / test，再用 buildx + QEMU
  构建 `linux/amd64` + `linux/arm64` 并推送到 GHCR。

## 风险与对策

| 风险 | 对策 |
|---|---|
| Supabase 打包器把 `node:sqlite` 内联进 Edge Function 产物导致云端启动失败 | 驱动实现改用「运行时拼接说明符」的动态 import，打包器无法静态追踪 |
| 两套 SQL 随时间漂移 | 方言翻译规则集中在一处并配套单测；新增语法必须同时加规则与测试 |
| Postgres 的 `jsonb` 与 SQLite 的 TEXT 返回类型不一致 | 路由层加 `parseJsonColumn()` 统一成对象 |
| 容器内无网络时启动失败 | 提交 `deno.lock`；镜像内完成依赖预热，已用 `--cached-only` 验证可离线运行 |
| 本地模式与 Supabase 模式的 URL 前缀不同易混淆 | `basePath` 显式参数化，README 中两处都写明 |
