## 踩过的坑

### 1. `Deno.loadEnvFile` 在当前 Deno 版本里不存在

先探测再动手，结果 `typeof Deno.loadEnvFile === "undefined"`（加 `--unstable` 也没有），
`--env-file-if-exists` 也不被识别。于是自研了一个 60 行的 `.env` 解析器，
顺便获得了「进程环境变量优先，不被文件覆盖」这个更合理的行为，Docker 里也能共用。

### 2. 模板标签函数的签名必须写成剩余参数

第一版把驱动实现写成：

```ts
const execute = async (strings: TemplateStringsArray, values: unknown[]) => { ... }
```

作为标签调用时 `values` 拿到的是**第一个插值本身**而不是数组，报
`values.map is not a function`。必须写成 `(strings, ...values: unknown[])`。

### 3. `jsonb` 与 `TEXT` 的返回类型不一致

Postgres 的 `jsonb` 列被 postgres.js 自动解析成对象；SQLite 存 TEXT，读出来是字符串。
直接照搬会让 `/api/build` 的 `Metadata` 在不同模式下形状不同。加
`parseJsonColumn()` 在路由层统一（两种驱动都能正确处理）。

### 4. `/api/latest` 的语义与直觉相反

写测试时我以为是「最大 id」，实际是「最近 100 个 changelist 中最早那条的 id」——
一个增量同步的起点。测试失败后核对 SQL 才发现是自己的理解错了，于是把测试断言
改成正确值并在断言旁写明语义。**这是测试帮我纠正理解、而不是代码有 bug 的一次典型情况。**

### 5. 让 Supabase 打包器别把 `node:sqlite` 内联进去

`drivers/sqlite.ts` 依赖 `node:sqlite`，而 Supabase Edge Runtime 不提供它。
如果打包器把两个驱动都静态内联进 Edge Function 产物，云端会在加载阶段直接失败。
对策是驱动加载写成运行时拼接的说明符：

```ts
const specifier = `./drivers/${name}.ts`;
const module = await import(specifier);
```

esbuild 无法静态追踪，只有真正选中该驱动时才会去加载。

### 6. 容器里没有 curl/wget

`denoland/deno:alpine-*` 是精简镜像，healthcheck 用不了 `curl`。
改成 `deno run --no-config --allow-net --allow-env tools/healthcheck.ts`，
既不依赖 shell，也不依赖额外二进制。

### 7. 依赖预热与离线运行

Dockerfile 分两阶段：第一阶段只复制 `deno.json`/`deno.lock` 预热依赖（改业务代码不会让该层失效），
第二阶段 `COPY --from=deps /deno-dir` 并再 cache 一次真实入口。

一开始想当然地认为「缓存了就能离线」，实测 `--no-remote` 会失败
（JSR 包清单解析需要联网），而 `--cached-only` 能正常启动——原因是 **`deno.lock` 已经把
版本范围解析结果固定下来了**。结论：`deno.lock` 必须提交，不能 gitignore。

### 8. `deno fmt` 会污染既有文件的 diff

跑了一次 `deno fmt` 后发现 `utils.ts` 被重排（原仓库本来就不是 fmt-clean，有些行超过 160 字符）。
于是把 `utils.ts` 回滚后只手工加上新增函数，避免把格式化噪音混进功能改动。
CI 里因此**只跑 `deno lint`**，不加 `deno fmt --check` 门禁。

## 一些设计取舍

- **SQLite 用 `node:sqlite` 而不是 `jsr:@db/sqlite`**：Deno 内置，零依赖、零原生模块编译。
  代价是必须用 Node 兼容层，但对本项目无影响。
- **方言翻译放在驱动层而不是路由层**：路由层保持「一份 Postgres 风格 SQL」，
  翻译规则集中在一个数组里，便于审计与测试。
- **事务嵌套用 SAVEPOINT**：当前项目只用了一处事务，但嵌套语义正确成本很低，顺手做了。
- **不做 SQLite → Postgres 的数据迁移工具**：超出本次需求范围；两种模式数据结构等价，
  需要时用现成工具（如 `pgloader`）即可。

# 后续：移除 Supabase / Cloudflare，收敛为纯 SQLite（同日晚些时候）

对应计划：[2026-09-18-移除Supabase收敛为纯SQLite.md](../plan/2026-09-18-移除Supabase收敛为纯SQLite.md)

## 决定

双模式落地后确认 Supabase 与 Cloudflare 这两个路径不会被使用。
它们的存在迫使整个项目长期承担「两套后端」的复杂度：
驱动抽象层、Postgres 方言翻译层、`jsonb` 与 TEXT 的类型差异处理、
`DB_DRIVER` / `BASE_PATH` 等只在云模式下有意义的配置，
以及一段纯粹为了绕开 Supabase 打包器的动态 import 代码。

于是删掉：`supabase/`、`cloudflare-proxy/`、`docker-compose.postgres.yml`、
PostgreSQL 驱动、方言翻译层。代码从 `supabase/functions/ugs-metadata/` 整体搬到根目录 `src/`。

## 删除清单与理由

| 删掉的东西 | 原本为了什么 | 为什么现在不需要 |
|---|---|---|
| `drivers/types.ts` + `drivers/postgres.ts` | 让两套后端共用一套路由 | 只剩一个后端 |
| `DIALECT_REWRITES` / `applyDialect` | 把 Postgres 风格 SQL 翻译成 SQLite | 路由直接写 SQLite 原生 SQL |
| 运行时拼接说明符的动态 import | 防止 Supabase 打包器内联 `node:sqlite` | 没有打包器了，改回普通静态 import |
| `basePath` | 吞掉 Supabase URL 里的 `/ugs-metadata` | 没有前缀了 |
| `DB_DRIVER` / `SUPABASE_DB_URL` / `DATABASE_URL` | 选择后端 | 只有一个后端 |
| `supabase/migrations/*.sql` | Postgres 建表 | 只维护 `src/schema.sql` |

## 顺带简化掉的东西

- `NOW() AT TIME ZONE 'utc'` 全部换成标准 SQL 的 `CURRENT_TIMESTAMP`，
  时间戳格式从 `YYYY-MM-DD HH:MM:SS.mmm` 简化为 `YYYY-MM-DD HH:MM:SS`
  （少了一层自研的 `strftime` 表达式，也少了一层毫秒精度带来的格式不一致）。
- 数据库生命周期从「读环境变量决定驱动 + 懒加载单例」改成显式的
  `initDatabase()` / `closeDatabase()`：`server.ts` 和测试各自调用一次，
  路由层只 `import { sql }`。好处是配置错误在启动阶段就暴露。
- `serve.ts` 改名 `server.ts` 并改用静态 import —— 之前全部写成动态 import
  只是为了让 `.env` 在 `db.ts` 读环境变量之前加载，现在这个顺序依赖不存在了。
- `deno.lock` 里 `npm:postgres` 消失，specifier 从 4 条降到 2 条。

## 过程中被测试抓出来的一个真 bug

`openDatabase({ applySchema: false })` 的用例失败，报
`AssertionError: Function throws when expected to reject`。

原因是 `execute()` 被写成了普通（非 async）函数，SQL 语法错误会**同步抛出**，
而接口签名声明的是 `Promise<Row[]>`。这会让调用方常用 `.catch(...)` / `Promise.all()` 处理错误的写法失效。

修在实现侧而不是测试侧：把同步异常统一包成 `Promise.reject(error)`，
恢复到「返回 Promise 的函数绝不同步抛错」这个约定。

## 回头看

上一版里那些「为了双模式而写」的代码，真正有价值的只有两小块：

1. **参数归一化**（`normalizeParam`）—— 因为 SQLite 的绑定接口确实不接受 boolean/undefined，
   这是真实约束，不是双模式带来的。
2. **预编译语句缓存 + 嵌套事务（SAVEPOINT）** —— 与后端无关的通用改进。

其余部分（方言翻译、驱动工厂、动态 import 绕行、`basePath`）在收敛后全部成为净负担。
教训：**不要为「可能用得上」的第二种后端提前抽象**，
这类抽象的维护成本是按路由数乘算的，而收益是零（除非第二种后端真的上线）。
